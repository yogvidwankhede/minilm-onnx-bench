# minilm-onnx-bench

[![ci](https://github.com/yogvidwankhede/minilm-onnx-bench/actions/workflows/ci.yml/badge.svg)](https://github.com/yogvidwankhede/minilm-onnx-bench/actions/workflows/ci.yml)

Production serving for my fine-tuned sentence-embedding model
[`yogvidwankhede/healthmate-minilm-l6-v2-medical-3fold`](https://huggingface.co/yogvidwankhede/healthmate-minilm-l6-v2-medical-3fold),
the retriever behind [HealthMate-AI](https://github.com/yogvidwankhede/HealthMate-AI).
It covers the path from PyTorch checkpoint to a running service:

- **Export** to ONNX with pooling and normalization inside the graph.
- **Release gate:** a model bundle is only produced if ONNX Runtime matches PyTorch within tolerance.
  On the real weights it rejected plain int8, which led to a measured quantization search.
- **Bundles** are content-addressed over every file; the server re-verifies checksums at startup
  and runs a golden-vector self-test before taking traffic.
- **Inference service:** OpenAI-compatible API, token-budget dynamic batching, all-or-nothing load
  shedding, request size limits, Prometheus metrics, JSON logs with no request text, a self-healing
  failure model, graceful drain.
- **Execution targets:** CPU, CoreML (Apple GPU / Neural Engine) and CUDA, each benchmarked for speed
  *and* fidelity.
- **Performance over time:** every push benchmarks the real model in CI, gates on regressions
  against the run history, and publishes a trend chart.
- **Container:** no PyTorch in the image, non-root, readiness-based health check.
- **CI:** lint, tests on Python 3.10 and 3.12, the release gate on the real weights, an image build
  plus container smoke test, and the performance gate.

## Quick start

```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -e ".[dev]"

make test                        # 72 tests, offline, about 15 s
make bundle                      # gated fp32 bundle from the fine-tuned weights (Hugging Face)
make bundle MODEL=standin        # same, from a same-architecture stand-in (no network)
make serve BUNDLE=bundles/<name> # http://localhost:8080
```

```bash
curl -s localhost:8080/v1/embeddings -H 'content-type: application/json' \
  -d '{"input": ["chest pain radiating to the left arm", "metformin side effects"]}'
```

Because the API matches OpenAI's embeddings endpoint, existing clients work unchanged:

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8080/v1", api_key="unused")
vec = client.embeddings.create(model="healthmate-minilm", input="shortness of breath").data[0].embedding
```

Container, and other hardware:

```bash
docker build --build-arg BUNDLE=bundles/<name> -t minilm-embed .
docker run -p 8080:8080 -e EMBED_INTRA_OP_THREADS=2 minilm-embed
EMBED_EXECUTION_TARGET=coreml make serve BUNDLE=bundles/<name>   # or cuda
python tools/target_bench.py --model <hf-id> --out results/<machine>/targets   # measure this machine
```

## Results on the fine-tuned weights

### The release gate caught plain int8 breaking retrieval

| Variant | Gate | Worst cosine vs PyTorch | Top-1 agreement |
|---|---|---:|---:|
| fp32 (default) | PASS | 1.0000000 (max abs diff 1.9e-07) | 1.00 |
| int8, ONNX Runtime default | **FAIL** | 0.9594 | 0.80 |
| int8, attention projections only | PASS | 0.9988 | 1.00 |

- Plain dynamic int8 changed the top document for 3 of 15 test queries, and the gate refused to
  ship it.
- The same gate had passed int8 on the random-weight stand-in at cosine 0.99995. Trained weights
  develop activation outliers that random ones don't.
- A search over six int8 configs found two that pass, by keeping the outlier-heavy MatMuls in fp32
  ([`quant_search.json`](results/healthmate/quant_search.json)).
- **On Apple Silicon none of them was faster than fp32**, so **fp32 is the default** and int8 is
  opt-in ([ADR 0003](docs/adr/0003-int8-dynamic-quantization.md)).

### Which runtime wins depends on the hardware and the workload

Apple M4 Max, fine-tuned weights; every fp32 target matched PyTorch to within 2e-07
([`targets.md`](results/healthmate/apple-m4-max/targets.md)):

| Workload | Fastest here | vs PyTorch CPU |
|---|---|---:|
| Single query, 32 tokens | ONNX Runtime CPU, 1.24 ms | 2.00x |
| Bulk, batch 8–32 | PyTorch on the Apple GPU (MPS) | 1.99x – 4.24x |
| Large batches on CPU | PyTorch CPU beats ONNX Runtime CPU | ORT 0.72x – 0.82x |
| Any shape | ONNX Runtime CoreML was slowest | 0.16x – 0.47x |

So on an Apple desktop the right split is ONNX Runtime for interactive queries and the GPU for bulk
indexing; on x86 servers it's ONNX Runtime CPU. CUDA support is implemented but unmeasured (no
NVIDIA hardware) ([ADR 0006](docs/adr/0006-execution-targets.md)).

### Performance over time

The CI `perf` job times ONNX Runtime against PyTorch with the real weights on every push. It fails on:
- a drop of more than 20% against the median of recent runs on the same runner class,
- a breach of a committed floor, or
- any fidelity loss.

On `main`, each run is appended to the
[`perf-history`](https://github.com/yogvidwankhede/minilm-onnx-bench/tree/perf-history) branch,
which renders the trend chart ([ADR 0007](docs/adr/0007-performance-over-time.md)).

## Results on the same-architecture stand-in

Measured before the fine-tuned weights were available, in a build workspace that couldn't download
them: a randomly initialized model with the identical architecture (6 layers, hidden 384, 22.6M
params), on a 2-vCPU x86 KVM guest with AVX-512 VNNI.

- **Latency transfers.** It depends on architecture and input shapes, not weights.
- **Fidelity does not.** The int8 result above is the proof.
- **Load-test sequence lengths only approximate real ones.** The load test tokenized with a small
  stand-in vocabulary.
- **The two vCPUs may share a physical core.** The guest reports one thread per core, but the
  host's mapping is unknown.

### Offline: ONNX Runtime vs PyTorch (x86)

| Variant | Size | Speedup vs PyTorch eager (range over 9 batch × sequence cells) |
|---|---:|---|
| ONNX fp32, ORT-fused | 90.2 MB | 1.11x – 2.68x |
| ONNX int8, dynamic quantization | 58.5 MB | 1.96x – 4.73x |

- The biggest fp32 gain is at batch 1 with short inputs, where eager-mode dispatch overhead
  dominates.
- **Unfused** fp32 ONNX was no faster than PyTorch at batch 32 in two cells: 0.93x at seq 128, and
  0.98x at seq 32, whose CI straddles 1.
- int8's speed here leans on VNNI; see the Apple results above for the other side.

Details: [`results/standin/results.md`](results/standin/results.md)

### Online: dynamic batching

int8 stand-in bundle, server pinned to one vCPU, load generator on the other, single-text
requests; median of 3 interleaved repetitions, with shaded min–max bands.

![load test](results/serving/loadtest.png)

| Policy | c=1 p50 | c=16 req/s · p50 | c=64 req/s · p50 |
|---|---:|---:|---:|
| No batching | 7.6 ms | 151 · 104 ms | 144 · 442 ms |
| **Batching, wait 0 ms (default)** | 7.7 ms | 222 · 69 ms | 220 · 279 ms |
| Batching, wait 5 ms | 13.0 ms | 210 · 71 ms | 196 · 321 ms |

Batching raises throughput 47–53% under load and cuts median latency by a third or more, with
non-overlapping ranges across repetitions. It costs nothing when idle as long as it doesn't *wait*:
requests that arrive while the model is busy form the next batch by themselves. Whether a 2 ms wait
beats 0 ms under heavy load is inside the noise; see [ADR 0004](docs/adr/0004-dynamic-batching.md).
Full table: [`results/serving/loadtest.md`](results/serving/loadtest.md).

### Measuring it honestly

The first load test said batching *collapses* at 64 concurrent clients. Before changing any code I
checked where the time went:

1. Pinned server and load generator to separate vCPUs. The collapse remained.
2. Compared a cold server with one that had already run lower load levels. Both collapsed, so it
   wasn't accumulated state.
3. Profiled the server (py-spy). Neither the ORT thread nor the event loop was saturated.
4. Compared server-side request time (from `/metrics`) with client-side latency. They disagreed by
   about 8x.
5. Swapped the load generator's HTTP client.

Same server, same load, only the client changed ([`results/serving/client_comparison.md`](results/serving/client_comparison.md),
median of 2 runs):

| Client, 64 connections | Req/s | Client p99 | Server-side time per request |
|---|---:|---:|---:|
| httpx | 81 | 3,146 ms | 64 ms |
| aiohttp | 194 | 482 ms | 297 ms |

The service was fine. httpx's async connection pool was the bottleneck under bursty responses, which
is exactly the pattern batching produces; at 16 connections both clients agree. The load test now
uses aiohttp, pins CPUs, repeats runs, and reports the server's own view next to the client's, so a
disagreement between them is visible instead of silently wrong. `--client httpx` reproduces the
problem.

## What is verified where

| Claim | Verified by |
|---|---|
| Real fine-tuned weights pass the gate (fp32) and plain int8 fails it | Apple M4 Max run (`results/healthmate/`); CI `bundle` job on every push |
| Export parity, dynamic shapes, padding invariance | `tests/test_pipeline.py` |
| Gate blocks bad bundles; tampered, mismatched or tokenizer-drifted bundles never become ready | `tests/test_serving.py` |
| Batching preserves order; fp32 is batch-invariant; int8 drift exists and is bounded | `tests/test_serving.py` · `results/serving/batch_drift.json` |
| Load shedding is all-or-nothing; timeouts and cancellations release work; a dead batcher fails fast and turns liveness red | `tests/test_serving.py` |
| API shape, validation, size limits, request-id sanitizing, error shapes, metrics | `tests/test_serving.py` |
| Quantization configs select the intended MatMuls; targets fail loudly when unavailable | `tests/test_targets_and_quant.py` |
| Performance gate fails on sudden regressions, floor breaches and fidelity loss | `tests/test_perf_gate.py`; CI `perf` job |
| CPU, Apple GPU (MPS) and CoreML speed and fidelity | `tools/target_bench.py` on Apple M4 Max |
| CUDA | **implemented, not measured** (no NVIDIA hardware available) |
| Docker image builds, is non-root, reads its bundle, becomes healthy, serves, drains | CI `image` job |

## Layout

```
src/minilm_onnx/
  model.py export.py parity.py      export + parity (build time, needs torch)
  quant.py                          int8 configs (per-channel, weights-only, fp32 exclusions)
  package.py                        gated bundle builder
  bench.py runtimes.py report.py    offline ONNX Runtime vs PyTorch benchmark
  serving/                          runtime, no torch
    bundle.py      manifest, checksums, content-addressed version, golden set
    tokenize.py    Rust tokenizer + padding (shared with the packager)
    providers.py   execution targets: CPU, CoreML, CUDA
    engine.py      admission, token-budget batcher, ORT worker, cache, failure handling, drain
    app.py         HTTP API, limits, errors, request ids, metrics endpoint
    config.py metrics.py logs.py __main__.py
tools/
  quant_search.py   int8 config search: fidelity vs speed
  target_bench.py   every execution target on this machine
  perf_gate.py      performance-over-time gate (CI)     perf_history.py  trend chart
  loadtest.py run_loadtest.sh report_loadtest.py batch_drift.py draw_architecture.py
perf/floors.json    committed performance floors
docs/               runbook, ADRs
requirements/       pinned serving lock file used by the Dockerfile (Python 3.11+)
```
